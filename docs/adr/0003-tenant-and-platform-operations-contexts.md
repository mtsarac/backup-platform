# 0003: Tenant requests use a filtered context, platform work a separate unfiltered one

Tenant isolation was carried by hand-written `TenantId ==` predicates in every store while the filtered tenant context sat unused. Tenant data is now reached through `PlatformDbContext` bound to the request's `ITenantContext` (global query filters plus a write guard), and platform-wide work (workers, agent identity and leases, authentication, platform administration) through `PlatformOperationsDbContext`, a distinct unfiltered type. We chose application-level isolation over PostgreSQL row-level security: the boundary stays in code review and architecture tests, and an architecture test pins the files that may name the unfiltered type, so using it from tenant code is a visible, reviewed exception. Stores that served both kinds of caller were split into a tenant store and a `*PlatformStore`; tenant operations that must write platform-owned rows (audit, notifications, storage connections, discovery inventory) do so through the platform-operations companion of their own transaction, so the write guard is never relaxed. Addresses [#258](https://github.com/mtsarac/backup-platform/issues/258).
